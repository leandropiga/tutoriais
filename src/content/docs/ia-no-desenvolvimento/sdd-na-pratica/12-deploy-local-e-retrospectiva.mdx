## Onde estamos

Este é o último capítulo do fluxo principal. No [anterior](/tutoriais/ia-no-desenvolvimento/sdd-na-pratica/11-validacao-e-dividas/) a validação manual passou e a rodada das dívidas foi mergeada.

**Ponto de partida:** o seu projeto ao fim do capítulo 11, com a rodada das dívidas mergeada na `main`.
**Tag de chegada:** `fase-8-retrospectiva`. A tag `fase-7-deploy` marca o fim do deploy local, antes da retrospectiva.

## O que vamos fazer e por quê

1. **Deploy.** Aqui, "deploy" significa **rodar a aplicação completa localmente**, como ficou decidido no ADR do capítulo 03. Antes de executar, vale reabrir essa decisão: o ADR foi escrito antes de existir código, e perguntar de novo custa um minuto.
2. **Retrospectiva.** Olhar para trás, para as etapas e decisões do projeto, e responder: o que funcionou, o que não funcionou e o que você faria diferente. Tudo sai dos ADRs, do `docs/rulings.md` e do Git.

## Passo a passo

### 1. Reabra a decisão do deploy

Releia o ADR do deploy local, em `docs/decisoes/`, e pergunte: agora que o código existe, essa decisão ainda vale?

- **Se vale,** siga com o deploy local, como neste capítulo.
- **Se quer publicar em nuvem,** trate isso como um novo ciclo de SDD (spec do que muda, plano, tarefas, análise) e registre a mudança num ADR novo. Este capítulo não cobre a nuvem, mas o passo 4 lista os pontos de atenção.

No meu caso, mantive o deploy local.

### 2. Planeje o deploy local

O deploy também vira tarefas, com escopo explícito, como as rodadas. Cole no Claude Code:

```text
Crie uma fase nova no fim do tasks.md, "Deploy local", com IDs novos, na sequência das tarefas
existentes, e com estas tarefas:

1. Se o frontend carrega telas sob demanda (React.lazy), um ErrorBoundary em volta das rotas:
   se uma tela falhar ao carregar, mostrar uma mensagem em português e um botão "Recarregar a
   página". Com teste.
2. Provar que o projeto sobe do zero: clonar o repositório numa pasta limpa, instalar as
   dependências, rodar as suítes e o build, e corrigir o README e o quickstart se faltar algum
   passo.
3. Uma seção "Onde publicar" no README.md, com sugestões de onde publicar e os pontos de
   atenção, sem passo a passo e deixando claro o que não foi testado.

Atualize o quadro de rodadas do ADR de implementação por rodadas com esta rodada.
```

Depois, peça a rodada como no capítulo 10, seguindo o ADR. Os passos 3 a 5 mostram o que conferir em cada tarefa.

### 3. Confira o ErrorBoundary

Se o seu frontend foi dividido em pedaços que carregam sob demanda (no capítulo 11, na rodada das dívidas), existe uma falha nova: se um pedaço não carregar (a rede caiu, ou o app foi atualizado e o nome do arquivo mudou), a tela fica em branco, sem explicação.

Confira se o agente criou o `ErrorBoundary` em volta das rotas, com um teste que simula a falha do carregamento e confere a mensagem e o botão.

No meu caso, foi um `ErroBoundary` (`frontend/src/components/erro-boundary.tsx`), uma classe React em volta do `Suspense` das rotas. O teste usa um `lazy` cujo import dá erro e confere a mensagem e o clique no botão "Recarregar a página".

Cada otimização cria um modo de falha novo. A resposta é tratá-lo, não escondê-lo.

### 4. Prove que roda na máquina de outra pessoa

"Roda na minha máquina" não prova nada. O teste de verdade é começar do zero: clonar numa pasta limpa, sem nenhum arquivo seu, e fazer tudo do início. Mesmo que o agente já tenha feito isso na rodada, faça você também:

```bash
# fora da pasta do projeto; use o nome que você deu ao repositório no capítulo 02
gh repo clone tutorial.sdd.contract clone-limpo
cd clone-limpo
cp backend/.env.test.example backend/.env.test
(cd backend && npm ci && npx vitest run)
(cd frontend && npm ci && npx vitest run && npm run build)
```

Os arquivos `.env` não vão para o Git: quem clonar precisa copiá-los dos exemplos antes de rodar os testes. Confira quais exemplos o **seu** projeto tem e se o README e o quickstart dizem para copiá-los.

No meu caso:

| Etapa | Resultado |
|---|---|
| `npm ci` backend e frontend | ok |
| Testes do backend | 27 arquivos, 309 testes passando |
| Testes do frontend | 15 arquivos, 78 testes passando |
| `npm run build` | ok, sem aviso de chunk grande |

Clone limpo pega arquivo esquecido e dependência que só existia por acaso. O roteiro de validação na tela você já fez no capítulo 11.

### 5. Confira a seção "Onde publicar"

Leia a seção nova do `README.md`. Ela deve trazer **sugestões** de onde publicar, **sem passo a passo**, e os pontos de atenção que ninguém testou. Confira se pelo menos estes aparecem:

- variáveis de ambiente no servidor, e nunca a chave do Gemini no frontend;
- cookies e CORS em domínio real, com HTTPS;
- **disco persistente para os PDFs** (em plataformas com disco descartável, os contratos somem a cada deploy);
- migrações a cada publicação (`npx prisma migrate deploy`), e o seed só na primeira;
- a instabilidade ocasional do Gemini.

No meu caso, as sugestões foram Render, Railway e VPS com Docker Compose.

Um deploy local também é uma decisão. É melhor terminar com o app rodando e um mapa honesto do que falta para publicar do que fingir que nuvem é trivial.

### 6. Feche o deploy com uma tag

Com a rodada do deploy mergeada na `main` e o clone limpo verde:

```bash
git push origin main
git tag -a fase-7-deploy -m "Fase 7 - Deploy local concluido"
git push origin fase-7-deploy
```

### 7. Faça a sua retrospectiva

Antes de ler a minha, escreva a sua. Comece pelos números, que o agente junta para você:

```text
Monte os números do projeto a partir do Git, dos ADRs em docs/decisoes/, do tasks.md e do
docs/rulings.md: quantidade de ADRs, tarefas, rodadas, commits, Rulings, linhas de código da
aplicação e de teste, e testes automáticos no backend e no frontend.
```

Depois, responda às três perguntas, com exemplos do **seu** projeto:

1. **O que funcionou?** Que etapa achou algo que você teria descoberto só no código?
2. **O que não funcionou, ou funcionou pela metade?** Onde o processo pesou mais do que ajudou? Que ferramenta ficou sem uso?
3. **O que você faria diferente?** Se começasse outro projeto amanhã, o que cortaria e o que adiantaria?

Separe o que é fato (está no Git, nos ADRs, nos Rulings) do que é opinião sua, e diga qual é qual. Salve tudo em `docs/retrospectiva.md`.

### 8. Compare com a minha retrospectiva

Esta é a minha, do laboratório. Leia depois de escrever a sua, e compare.

**O laboratório em números:**

| O quê | Quanto |
|---|---|
| Decisões registradas (ADRs) | 11 |
| Tarefas no `tasks.md` | 86, todas concluídas |
| Rodadas de implementação | 7, mais a validação manual e o deploy local |
| Commits no Git | cerca de 120 |
| Código da aplicação | cerca de 6,7 mil linhas |
| Código de teste | cerca de 5,3 mil linhas |
| Testes automáticos | 387 (309 no backend e 78 no frontend) |

A proporção chama a atenção: quase uma linha de teste para cada linha de código. Não foi acidente. A constituição exigia testes, e o fluxo começava sempre pelo teste vermelho.

**O que funcionou:**

1. **Gastar tempo nos documentos antes do código.** O `/speckit-analyze` achou uma falha de segurança e uma violação da constituição antes de existir código. O `/speckit-plan` levantou o conflito dos 50 MB do Gemini. O `/speckit-clarify` fez duas perguntas que eu nem tinha no roteiro. *Errar num documento custa uma linha; errar em produção custa um dia.*
2. **Constituição com regras que dá para testar.** "Apagar o arquivo temporário inclusive em caso de erro" virou teste automático, e o passo 14 do roteiro manual conferiu na prática. Regra vaga não vira trava.
3. **Tarefas por história, não por camada.** Cada rodada terminava com algo que dava para abrir e usar.
4. **Revisão em duas camadas.** A de tarefa pega defeito local; a final da branch pega o que só se vê no conjunto (o furo de concorrência no bloqueio de login, as mensagens duplicadas, o `EXDEV` combinado com o `PUT`).
5. **O ledger e os Rulings.** Deixar o agente decidir só é seguro se as decisões ficarem escritas.
6. **Registrar o erro, não só o acerto.** As lições que mais valem estão nos tropeços do caminho: o 503 que só o log explicou, o `.env` que só é lido na partida, o fallback do `EXDEV` que estragava o PDF.

**O que não funcionou (ou funcionou pela metade):**

1. **A extensão `bug` do Spec Kit ficou sem uso.** Eu tinha planejado que bugs reais passariam pelo fluxo `/speckit-bug-assess`, `-fix` e `-test` (veja o [capítulo 13](/tutoriais/ia-no-desenvolvimento/sdd-na-pratica/13-extras/)). Na prática, **nenhum** dos bugs da implementação passou por ele: foram achados e resolvidos dentro do ciclo de revisão do Superpowers (revisor, correção, re-revisão). Há duas leituras honestas: ou o ciclo do Superpowers já cobre o mesmo terreno e o `bug` é redundante dentro de uma rodada, ou o `bug` serviria para defeitos achados **depois** da rodada (como o 503 do Gemini) e eu simplesmente não tive nenhum desses. Minha opinião é a segunda, mas **não testei**. Não prometo esse fluxo como se tivesse sido exercitado.
2. **Os scripts do Superpowers esperam um formato de plano que o Spec Kit não gera.** O `task-brief` procura títulos "Task N" e o meu `tasks.md` usa `T001`. Em duas rodadas escrevi os pedidos à mão. Funciona, mas é um atrito de juntar as duas ferramentas.
3. **Subagentes precisam de cerca.** Um com acesso ao terminal fez estrago fora do projeto; outro usou `git stash` num worktree compartilhado. A lição foi a mesma duas vezes: diga o que o agente **não** pode fazer.
4. **O processo é pesado para o tamanho do problema.** Para uma aplicação de um usuário só, a cerimônia é grande: 11 ADRs, 7 rodadas, revisões em camadas. Faz sentido **porque o objetivo era estudar o processo**. Num projeto real e pequeno, eu cortaria: menos rodadas, uma revisão final só, ADRs só para divergências de verdade. Isso é opinião minha.
5. **Tudo foi feito por quem acompanhou o tempo todo.** Os pontos de "pare e pergunte" funcionaram, mas o laboratório não mostra o que acontece quando **ninguém está olhando**. Rulings errados custam retrabalho, e eu só descobri os meus porque alguém leu a lista no fim.
6. **Dívidas acumuladas.** Anotei dívidas rodada a rodada e só fechei cinco. Ficaram em aberto, de propósito: acessibilidade do menu de perfil e do gráfico, "tentar de novo" na Home, alguns testes menores. **Dívida anotada não é dívida paga.**

**O que eu faria diferente:**

1. Começar com o ledger e os Rulings desde a primeira tarefa.
2. Ter um `ErrorBoundary` e o tratamento de erro de rede **no plano**, e não como dívida da rodada 7. Quem divide o bundle precisa saber que um pedaço pode não carregar.
3. Rodar o roteiro manual **por pedaços, ao fim de cada rodada**, não tudo no final.
4. Decidir cedo a regra dos arquivos de configuração local (`.env`, `.env.test`) e ter um script de "preparar ambiente". Eu os recriei à mão em quase toda rodada.
5. Definir antes que só vou prometer o que foi exercitado. Vale para a extensão `bug`.

**O que levar daqui, em sete linhas:**

1. **Documento antes de código.** Constituição, spec, clarify, plano e analyze achando coisa de verdade.
2. **Dois frameworks, dois papéis.** Spec Kit decide o *quê*; Superpowers decide o *como*. (Era o meu experimento: não há certo ou errado.)
3. **Regras testáveis.** Se não dá para virar teste, não é regra.
4. **Deixe o agente decidir, mas faça ele escrever o que decidiu.**
5. **Revise a branch inteira, mesmo com tudo verde.**
6. **Conte os tropeços.**
7. **Seja claro sobre o que ficou de fora**: nuvem, acessibilidade, o fluxo `bug`, as dívidas.

### 9. Feche o ciclo

Commite a sua retrospectiva e marque o fim do projeto:

```bash
git add docs/retrospectiva.md
git commit -m "docs: retrospectiva do projeto"
git push origin main
git tag -a fase-8-retrospectiva -m "Fase 8 - Retrospectiva"
git push origin fase-8-retrospectiva
```

## O que esperar

- A aplicação rodando inteira na sua máquina: banco em Docker, backend em `http://localhost:3000`, frontend em `http://localhost:5173`.
- Uma fase "Deploy local" no `tasks.md`, toda marcada `[X]`.
- Um clone limpo com testes verdes e build sem aviso.
- Um `README.md` com a seção "Onde publicar" e a lista do que **não** foi testado.
- A sua retrospectiva em `docs/retrospectiva.md`.
- As tags `fase-7-deploy` e `fase-8-retrospectiva` no remoto, em commits diferentes.

## Divergências comuns

- **O clone limpo falhou.** Ótimo: foi para isso que você o fez. Quase sempre é um arquivo local que não está no Git (`.env.test`, `.env`) ou uma dependência que só existia na sua máquina. Corrija e documente.
- **O seu frontend não foi dividido em pedaços.** Então o `ErrorBoundary` da fase de deploy não é obrigatório. Ainda assim, vale ter um para erros de renderização.
- **Seus números são outros** (testes, linhas, commits). Esperado. Eles dependem do que o seu agente escreveu. Compare a estrutura, não os totais.
- **Você quer publicar em nuvem.** O laboratório não validou isso. Comece pela lista de pontos de atenção do passo 5, e trate o que você descobrir como um novo ciclo de SDD: spec do que muda, plano, tarefas, análise.
- **A sua retrospectiva concluiu o contrário da minha** (por exemplo, que o fluxo `bug` vale a pena, ou que SDD é pesado demais). Não tem certo ou errado. Escreva por quê.

**Para comparar com o laboratório:** tags [`fase-7-deploy`](https://github.com/leandropiga/arkhos.labs.sdd.contract/tree/fase-7-deploy) e [`fase-8-retrospectiva`](https://github.com/leandropiga/arkhos.labs.sdd.contract/tree/fase-8-retrospectiva).

## O que aprendemos

- **"Roda na minha máquina" não prova nada.** Clone limpo prova mais.
- **Cada otimização cria um modo de falha novo.**
- **Reabra uma decisão antiga quando chega a hora de executá-la.** Ela foi tomada antes de existir código.
- **Os melhores achados do processo vieram dos documentos e da revisão final, não do código.** A frase que resume: errar num documento custa uma linha; errar em produção custa um dia.
- **O processo é uma ferramenta, não uma religião.** Pesado demais para um app pequeno? Corte. O importante é você saber o que cada etapa evita.
- **Prometa só o que foi exercitado.** O que ficou de fora (a nuvem, a acessibilidade, o fluxo `bug`) deve ser dito.
