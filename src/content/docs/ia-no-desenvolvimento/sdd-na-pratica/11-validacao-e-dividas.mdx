## Onde estamos

No [anterior](/tutoriais/ia-no-desenvolvimento/sdd-na-pratica/10-revisao-em-camadas/) todas as rodadas do `tasks.md` foram mergeadas, com a suíte toda verde.

**Ponto de partida:** o seu projeto ao fim do capítulo 10 (tag `fase-5-implementacao`), com o Docker disponível.
**Tag de chegada:** `fase-6-validacao`, que marca o fim da validação manual (passos 1 a 6 abaixo). A rodada das dívidas (passos 7 a 9) vem depois e termina no merge, sem tag.

## O que vamos fazer e por quê

Os testes automáticos dizem que o código faz o que combinamos. Mas ninguém ainda **usou a aplicação de verdade**, e a IA ainda só foi chamada por um dublê. Esta etapa faz duas coisas:

1. **Validação manual.** Seguir o roteiro de validação do `quickstart.md`, na tela, com a chave real do Gemini, e anotar o que acontece.
2. **Uma rodada para as dívidas.** Ao longo das rodadas, ficaram anotadas "dívidas": coisas que não quebravam nada, mas que incomodariam em produção. Antes de pensar em deploy, vale escolher as que mexem com produção ou segurança e fechá-las.

## Passo a passo

### 1. Monte o ambiente

O `backend/.env` não vai para o Git, então você cria a partir do exemplo e preenche com as variáveis que o seu `.env.example` pede. Para a validação com IA você precisa de uma chave da API do Gemini. Se não tiver, pule os passos do roteiro que chamam a IA; o resto funciona.

No meu caso, os comandos foram estes:

```bash
docker compose up -d
cd backend
cp .env.example .env     # preencha GEMINI_API_KEY, JWT_SECRET, SEED_USUARIO e SEED_SENHA
npm ci
npx prisma migrate deploy
npm run seed             # cria o primeiro usuário a partir de SEED_USUARIO / SEED_SENHA
npm run dev              # API em http://localhost:3000
```

Em **outro terminal**:

```bash
cd frontend
npm ci
npm run dev              # app em http://localhost:5173
```

Os nomes das variáveis e dos scripts (`seed`, `dev`) vêm do plano. Confira os seus no `quickstart.md` e nos `package.json`.

Os dois servidores de desenvolvimento não terminam. Se você juntar migração, seed e servidores num comando só, ele nunca volta, ou estoura o tempo limite. Rode cada passo separado.

Atenção a um detalhe: sem `node_modules` na pasta, o `npx prisma` baixa a versão mais recente do Prisma, que pode ser outra versão principal, com outros comandos. Rode `npm ci` nas duas pastas **antes** de qualquer `npx`.

### 2. Gere os PDFs de teste

O roteiro tem um passo de upload que testa três casos: um PDF válido, um texto puro com extensão `.pdf` e um PDF acima de 50 MB. Este script cria os três na pasta atual:

```javascript
import { writeFileSync, appendFileSync } from 'node:fs';

const pdf = (texto) => {
  const conteudo = `BT /F1 12 Tf 72 720 Td (${texto}) Tj ET`;
  return [
    '%PDF-1.4',
    '1 0 obj << /Type /Catalog /Pages 2 0 R >> endobj',
    '2 0 obj << /Type /Pages /Kids [3 0 R] /Count 1 >> endobj',
    '3 0 obj << /Type /Page /Parent 2 0 R /MediaBox [0 0 612 792] /Contents 4 0 R /Resources << /Font << /F1 5 0 R >> >> >> endobj',
    `4 0 obj << /Length ${conteudo.length} >> stream\n${conteudo}\nendstream endobj`,
    '5 0 obj << /Type /Font /Subtype /Type1 /BaseFont /Helvetica >> endobj',
    'trailer << /Root 1 0 R >>',
    '%%EOF',
    '',
  ].join('\n');
};

writeFileSync('1-contrato-valido.pdf', pdf('Contrato de compra e venda. Multa de 20 por cento por rescisao antecipada. Foro: Sao Paulo.'));
writeFileSync('2-falso-texto-renomeado.pdf', 'isto e texto puro, nao e um PDF\n');
writeFileSync('3-grande-demais-51MB.pdf', pdf('grande demais'));
appendFileSync('3-grande-demais-51MB.pdf', Buffer.alloc(51 * 1024 * 1024));
```

Salve como `gerar.mjs` e rode `node gerar.mjs`. O PDF válido é mínimo; se o seu navegador ou a IA reclamarem dele, use qualquer PDF pequeno de verdade.

### 3. Siga o roteiro

Abra o **seu** `quickstart.md` e ache a seção de validação: uma tabela de passos, cada um com o resultado esperado. Siga na ordem, na tela, e anote o resultado de cada passo.

No meu caso, o roteiro tinha 14 passos:

| # | História | Passos | Resultado esperado |
|---|---|---|---|
| 1 | Login (P1) | Abrir `http://localhost:5173/clientes` sem login | Vai para `/login` |
| 2 | Login (P1) | Entrar com o usuário do seed | Menu com Home, Clientes e Contratos |
| 3 | Login (P1) | Sair; errar a senha 5 vezes; tentar a senha certa | Aviso de bloqueio temporário; após 15 min entra |
| 4 | Clientes (P1) | Cadastrar 2 clientes em UFs diferentes; tentar repetir um CPF | Lista com os 2; CPF repetido recusado |
| 5 | Clientes (P1) | Filtrar por parte do nome sem acento; filtrar por CPF com pontuação | Só os clientes certos aparecem |
| 6 | Contratos (P2) | Cadastrar contrato com PDF; tentar com um `.txt` renomeado para `.pdf`; tentar com um PDF acima de 50 MB | Primeiro aceito; os outros dois recusados com mensagem |
| 7 | Contratos (P2) | Filtrar por título e por período; abrir o detalhe; abrir o PDF | Filtros corretos; PDF abre |
| 8 | Clientes (P1) | Tentar excluir o cliente que tem contrato | Bloqueado, com a quantidade de contratos |
| 9 | Análise (P3) | No detalhe do contrato, "Solicitar Análise de PDF" | Painel com resumo, riscos e cláusulas; data de geração |
| 10 | Análise (P3) | Sair da tela e voltar | Análise continua visível |
| 11 | Análise (P3) | Com `GEMINI_API_KEY` inválida no `.env`, pedir análise | Toast "serviço de análise temporariamente indisponível"; análise anterior continua |
| 12 | Painel (P4) | Abrir a Home | Gráfico por UF e totais batem com os cadastros |
| 13 | Perfil (P5) | Alterar nome, foto (URL) e telefone | Nome e foto aparecem no menu |
| 14 | Arquivos | Após os passos 6 e 9, listar `backend/tmp/uploads` | Diretório vazio (Princípio IV) |

O seu roteiro pode ter outra numeração e outros passos. Alguns merecem atenção, em qualquer versão:

- **O passo da pasta de uploads** (no meu caso, o 14) é a regra da constituição ("apagar inclusive em caso de erro") conferida na prática: a pasta deve estar **vazia** depois de um upload bem-sucedido, um recusado e uma análise.
- **No passo do bloqueio de login,** você não precisa esperar os 15 minutos do desbloqueio: basta conferir o aviso.
- **Os passos da análise** dependem de um serviço externo. Os passos 4 e 5 abaixo explicam o que fazer quando eles falham.

O esperado é que todos os passos passem. Se algum falhar, siga para o próximo passo antes de mexer no código.

### 4. Se um passo falhar, leia o log antes de mexer no código

A mensagem da tela é genérica de propósito; o motivo de verdade está no log do servidor. Antes de mudar qualquer coisa:

1. **Anote** o passo, o que você fez e o que apareceu.
2. **Leia o log do backend** no terminal onde ele roda.
3. **Decida o tipo do problema:**
   - **Serviço externo fora do ar:** espere e repita (veja o exemplo abaixo).
   - **Bug no código:** peça a correção ao agente **com teste primeiro**, como uma tarefa nova no `tasks.md`, e não como um remendo direto.
   - **A spec não dizia o que fazer:** corrija a spec antes, e depois o código, na ordem do SDD.

No meu caso, o passo da análise mostrou na tela "serviço de análise temporariamente indisponível". O log do backend mostrava o que o Google tinha devolvido:

```text
503 UNAVAILABLE: This model is currently experiencing high demand.
Spikes in demand are usually temporary. Please try again later.
```

Se a chamada chegou ao Gemini, a chave está certa, e o **modelo estava sobrecarregado**. O app fez o certo: mapeou o erro para `503 IA_INDISPONIVEL` e mostrou a mensagem combinada, sem vazar nada técnico (Princípio III). Esperei um pouco, repeti, e a análise funcionou sem mexer em código.

**Leia o log antes de "consertar".**

### 5. Para simular a chave inválida, reinicie o backend

O roteiro tem um passo que testa a chave inválida (no meu caso, o 11). Trocar a `GEMINI_API_KEY` no `backend/.env` **não basta**: o servidor lê o arquivo só ao subir, e o `tsx watch` vigia o código, não o `.env`. Depois de trocar a chave, reinicie o backend. E reinicie de novo depois de restaurar a chave certa.

No macOS/Linux, basta `Ctrl+C` no terminal do backend e `npm run dev` outra vez. No Windows, se o terminal não estiver à mão, pare o processo que escuta na porta 3000 e suba de novo:

```powershell
Get-NetTCPConnection -LocalPort 3000 -State Listen | ForEach-Object { Stop-Process -Id $_.OwningProcess -Force }
```

```bash
cd backend && npm run dev
```

### 6. Feche a validação com uma tag

Com todos os passos do roteiro passando, e o resultado de cada um anotado, a validação manual está feita. Confira com `git status` se não ficou nada para commitar e marque o ponto:

```bash
git tag -a fase-6-validacao -m "Fase 6 - Validacao concluida"
git push origin fase-6-validacao
```

### 7. Escolha as dívidas

As dívidas ficaram espalhadas: Rulings de "adiar" no `docs/rulings.md`, achados menores das revisões e itens que você mesmo anotou. Peça ao agente para juntar tudo:

```text
Liste as dívidas técnicas anotadas ao longo da implementação: os Rulings que adiaram algo em
docs/rulings.md, os achados Minor das revisões e os itens que ficaram para depois. Para cada uma,
diga o risco e se ela mexe com produção ou segurança.
```

Escolha as que **mexem com produção ou segurança**. As outras ficam anotadas, de propósito. Anotada não é paga, mas escolher é melhor que tentar fechar tudo.

Depois, peça a fase nova:

```text
Crie uma fase nova no fim do tasks.md, "Dívidas técnicas antes do deploy", com uma tarefa para
cada dívida escolhida: <liste aqui>. Use IDs novos, na sequência das tarefas existentes, e
atualize o quadro de rodadas do ADR de implementação por rodadas com esta rodada.
```

Essas tarefas não estavam no `tasks.md` original. Divergir do plano está certo, desde que fique escrito: a fase nova dá à rodada um escopo explícito, como manda o ADR.

### 8. Rode a rodada das dívidas

Peça a rodada como no capítulo 10, seguindo o ADR. Leia a revisão final e os Rulings como nas outras rodadas.

No meu caso, foram cinco tarefas, numa "Fase 10" (T079 a T083):

| Tarefa | O problema | A correção |
|---|---|---|
| T079 | `rename` falha com `EXDEV` quando a pasta temporária e o storage ficam em volumes diferentes (comum em Docker) | se der `EXDEV`, copia e apaga o temporário |
| T080 | o download do PDF não dizia ao navegador para não guardar cache nem adivinhar o tipo | `Cache-Control: private, no-store` e `X-Content-Type-Options: nosniff` |
| T081 | **corrida no `PUT` do contrato**: a transação confirmava *antes* de o PDF novo entrar no storage; uma análise pedida nesse intervalo lia o PDF antigo e gravava como se fosse do novo | o `rename` do PDF passou para *dentro* da transação, antes do commit |
| T082 | `fotoUrl` aceitava texto de qualquer tamanho | máximo de 2048 caracteres, no backend e no formulário |
| T083 | o frontend era um arquivo só de 964 kB (o Vite avisava) | `React.lazy` nas telas e grupos de vendor |

Backend e frontend não se tocam, então essas tarefas rodaram em paralelo. A T081 foi sozinha: mexe em concorrência, e os testes do backend dividem o mesmo banco, então dois rodando juntos se atropelariam.

**A corrida do `PUT`, explicada.** Antes, a ordem era: (1) grava no banco e confirma; (2) move o PDF novo para o storage. Entre o 1 e o 2 existia um intervalo minúsculo em que o banco já dizia "contrato novo", mas o arquivo ainda era o velho. O teste que prova isso falhou primeiro, como deve: ele pausa o `PUT` exatamente no `rename` e dispara a análise nesse momento. Depois da correção, o `update` da linha segura um *lock* no Postgres, e a trava do `POST /analise` espera esse lock soltar.

A correção trocou um problema por outro menor: se o commit falhar *depois* do `rename`, fica o PDF novo com a linha antiga. Ficou aceito, por escrito, como Ruling.

**Resultado do bundle (T083):**

| | Antes | Depois |
|---|---|---|
| Arquivo JS | 1 de 964,61 kB | maior: `home` com 361,68 kB (gráfico) |
| Carregado de início | 964 kB | 542 kB |
| Aviso do Vite (>500 kB) | sim | sumiu |

**A revisão final achou um defeito na junção de duas tarefas.** Ela aprovou as cinco tarefas, sem nada Critical, mas achou um **Important** de verdade: o fallback do `EXDEV` (T079) copiava *por cima* do PDF do contrato. Se a cópia morresse no meio, o PDF ficava truncado, e no `PUT` o banco desfazia, mas o arquivo antigo já tinha sido estragado. Cada tarefa estava certa sozinha; a costura entre a T079 e a T081 não. A correção foi copiar para `<destino>.<uuid>.part` na mesma pasta e só então fazer `rename`, que é atômico.

### 9. Feche a rodada

Mesma sequência do capítulo 10: merge local, testes de novo na `main` e push. Esta rodada não tem tag própria: o próximo ponto marcado é o deploy, no capítulo 12.

## O que esperar

- Todos os passos do roteiro de validação concluídos, com o resultado de cada um anotado.
- A pasta de uploads temporários vazia ao fim.
- A tag `fase-6-validacao` no remoto, no fim da validação.
- Uma fase nova de dívidas no `tasks.md`, toda marcada `[X]` e mergeada na `main`.
- Suítes verdes e o build do frontend sem o aviso de chunk grande. No meu caso, foram 309 testes no backend e 76 no frontend.

## Divergências comuns

- **A análise devolve "serviço indisponível".** Leia o log do backend antes de qualquer coisa. Se for 503 do Google, espere e repita. Se for 400 ou 403, a chave está errada ou sem permissão.
- **Você não tem chave do Gemini.** Pule os passos que chamam a IA. O resto do roteiro vale.
- **O modelo do Gemini do plano (no meu caso, `gemini-3.8-flash`) não existe mais ou mudou.** Serviço externo muda. Troque pelo modelo equivalente atual, registre num ADR e repita o passo da análise.
- **A troca de chave não surtiu efeito.** Reinicie o backend. O `.env` só é lido na partida.
- **A sua lista de dívidas é outra.** Normal. Escolha as que mexem com produção ou segurança e deixe as outras anotadas. No meu caso, ficaram em aberto, de propósito, a acessibilidade do menu de perfil e do gráfico, o "tentar de novo" na Home e alguns testes menores.
- **Os números de tamanho do bundle são diferentes.** Dependem das versões. O que vale é o aviso sumir e o carregamento inicial ficar abaixo dos 500 kB.

**Para comparar com o laboratório:** tag [`fase-6-validacao`](https://github.com/leandropiga/arkhos.labs.sdd.contract/tree/fase-6-validacao). Ela marca o fim da validação manual, então a rodada das dívidas não está nela.

## O que aprendemos

- **Mudou o `.env`? Reinicie o servidor.** Variáveis de ambiente são lidas só na partida.
- **Uma IA externa vai ficar indisponível de vez em quando.** Tratar isso com mensagem amigável não é capricho, é requisito.
- **Testar com a chave real mostra o que o dublê esconde.**
- **Leia o log antes de consertar.** E, se for bug, corrija com teste primeiro, como qualquer outra tarefa.
- **Consertar uma coisa pode abrir outra.** O fallback do `EXDEV` estava certo sozinho, mas junto com o `PUT` virou risco. Quem achou foi a revisão olhando as duas juntas.
- **Teste de corrida precisa de um gancho no ponto exato**, não de `sleep` e sorte.
- **Dividir o bundle traz uma falha nova:** se um pedaço não carregar (por exemplo depois de um deploy, com nome de arquivo antigo), a tela quebra. Se dividir o bundle, planeje um `ErrorBoundary` junto.
- **Divergir do plano é ok, se ficar escrito.**
