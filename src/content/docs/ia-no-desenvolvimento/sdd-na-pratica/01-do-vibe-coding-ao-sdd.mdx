## O que vamos fazer e por quê

Se você já usa IA para programar, muito provavelmente é jeito que quase todo mundo começa: descreve o que quer, recebe código, ajusta até funcionar, segue em frente. Isso tem nome, **vibe coding**, e funciona bem para um script, um protótipo, uma tarefa pequena.

O problema aparece quando o que você pede tem regras que só existem na sua cabeça. A IA não tem como adivinhar que o CPF não pode repetir, que o upload precisa ser apagado mesmo se der erro, ou que a API externa só aceita 50 MB. Ela chuta. Você descobre o chute depois, no código, que é o lugar mais caro para descobrir.

**SDD (Spec-Driven Development, desenvolvimento guiado por especificação)** inverte a ordem: antes de pedir código, você escreve **o que** o sistema deve fazer, numa especificação (a *spec*). A spec vira a fonte da verdade, e o código passa a ser consequência dela. Quando a spec muda, o código acompanha, e não o contrário.

Em uma tabela, a diferença de rotina fica assim:

| | Vibe coding | SDD |
|---|---|---|
| Ponto de partida | Um prompt com o que você quer agora | Uma spec escrita e revisada |
| Onde as dúvidas aparecem | No código, quando algo quebra | No documento, antes do código |
| O que guia a IA | O seu prompt do momento | Regras e spec que ficam no repositório |
| Como você sabe que acabou | "Parece que funciona" | Critérios escritos, viram teste |
| Custo de corrigir um erro de entendimento | Reescrever código | Em geral, mudar texto (e propagar) |

Isso não é de graça. SDD gasta tempo e tokens em documentos antes da primeira linha de código. O resto do tutorial existe para você ver, numa aplicação de verdade, se esse custo se paga.

## Exercício: liste as decisões que a IA tomou por você

Antes de instalar qualquer coisa, um exercício de dois minutos. Ele mostra o problema sem precisar de ferramenta nenhuma.

1. Pegue uma funcionalidade que você pediu para a IA na última semana, em vibe coding.
2. Abra o código que ela gerou e liste **cada decisão** que ele tomou e que o seu prompt não pedia: limite de tamanho, o que fazer em caso de erro, formato de mensagem, o que acontece com dados duplicados, o que acontece quando a rede cai.
3. Para cada item, responda: eu concordaria com essa decisão se tivesse sido perguntado?

Anote o resultado. Se você é como eu fui, a lista passa de cinco itens, e pelo menos um você teria decidido diferente.

Cada item dessa lista é o que o SDD chama de **ambiguidade**: um ponto da spec que, sem resposta, vira chute. As etapas do SDD que você vai ver nos próximos capítulos existem para achar esses pontos antes do código.

## O que esperar do exercício

Ao terminar o exercício acima, você deve ter uma lista curta de decisões implícitas, e a sensação de que você faz esse trabalho de qualquer forma, só que no fim e sem registro. É isso que o SDD tenta puxar para o começo.

Para você reconhecer o tipo de item que procura, dois exemplos práticos de decisão implícita:

1. **Upload de arquivo.** Você pediu "endpoint para anexar um PDF ao contrato". O código gerado aceita qualquer tamanho, grava o arquivo em disco com o nome original e, se o insert no banco falhar depois, deixa o arquivo órfão no disco. Seu prompt não falou de limite de tamanho, de nome do arquivo nem de rollback. A IA decidiu os três, e você só descobre quando o disco enche ou quando dois clientes sobem um `contrato.pdf` e um sobrescreve o outro.
2. **Cadastro com dado único.** Você pediu "cadastro de cliente com CPF". O código cria o cliente sem checar duplicidade, ou checa e devolve um 500 genérico em vez de um 409 com mensagem clara. Também não define se `123.456.789-09` e `12345678909` são o mesmo CPF. Cada escolha é razoável, mas nenhuma foi sua, e o frontend acaba tratando o erro de um jeito que ninguém combinou.

Em cada caso, se alguém tivesse perguntado "qual o limite?", "o que acontece se falhar?" ou "CPF repetido devolve o quê?", você teria uma resposta. O SDD obriga a fazer essas perguntas antes de existir código.

Não há nada para conferir com comando neste capítulo. O critério é a sua própria lista.
