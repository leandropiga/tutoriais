## O que vamos fazer e por quê

Vamos transformar a spec (o *quê*) num **plano técnico** (o *como*): estrutura de pastas, modelo de dados, rotas da API, versões dos pacotes e como cada regra da constituição vai ser cumprida. Ainda sem escrever código.

O `/speckit-plan` trabalha em duas fases:

- **Fase 0, pesquisa** (`research.md`): resolve as dúvidas técnicas. Para cada decisão registra o que foi escolhido, por quê, e quais alternativas foram descartadas.
- **Fase 1, design**: `data-model.md` (entidades), `contracts/api.md` (rotas e erros) e `quickstart.md` (como subir e validar).

Antes e depois do design, o plano passa pelo **Constitution Check**: uma tabela que confere, princípio por princípio, se o plano obedece à constituição.

Esta etapa me ensinou a lição mais importante do tutorial até aqui. Spoiler: o plano encontrou um erro que eu tinha plantado de propósito.

### 2. Escreva (ou use) o prompt

O silêncio sobre os 50 MB é **de propósito**. Eu queria que o conflito estourasse mais tarde, na implementação. Num projeto real, você leria os limites da API antes. Leia o que aconteceu de verdade logo abaixo.

- Node.js 24 LTS e npm. Docker com Docker Compose v2 ou superior: o docker-compose.yml NÃO usa
  o campo `version`, que é obsoleto.
- A aplicação roda somente na máquina local (sem deploy em nuvem nesta versão). Backend,
  frontend e banco sobem com comandos documentados no quickstart.
- Use as versões estáveis mais recentes de cada pacote, conferidas no registro do npm no momento

- Configuração por variáveis de ambiente, com um `.env.example` para cada pacote que precisar.

## Backend

- API REST em JSON, sob o prefixo `/api`.

- O primeiro usuário é criado por um script de seed, com usuário e senha lidos de variáveis de

- Sessão: JWT em cookie HttpOnly (constituição), com validade de 8 horas, SameSite=Lax e Secure

- O bloqueio de login após 5 erros (FR-002) precisa sobreviver a uma reinicialização do

### 3. O que a pesquisa encontrou

O agente consultou o npm e a documentação oficial. Três achados reais.

**a) Uma armadilha no npm.** A tag `latest` do pacote `prisma` apontava para uma versão de teste:

```bash
npm view prisma dist-tags --json
# "latest": "8.0.0-rc.22"   <- release candidate!
npm view @prisma/client dist-tags --json
# "latest": "7.10.0"
```

Um `npm install prisma` ingênuo instalaria uma RC incompatível com o client. O plano fixou 7.10.0 nos dois. Sempre confira os `dist-tags` quando uma versão parecer estranha.

**b) A documentação do Gemini mudou.** Os exemplos atuais usam uma API nova (`ai.interactions.create`). O plano manteve `generateContent` com `response.text`, e conferiu nas definições de tipo do SDK que `response.text` é uma propriedade, não um método. A API nova ficou registrada como alternativa.

**c) O limite de 50 MB do Gemini.** Aqui está a virada.

### 4. O bug que nunca aconteceu

Na pesquisa, o `/speckit-plan` leu a documentação do Gemini e escreveu no `research.md`:

> A spec (FR-017) aceita PDFs de até **100 MB**. Logo, contratos entre 50 e 100 MB serão aceitos no cadastro, mas a análise deles vai falhar, e trocar de inline para File API **não** resolve.

E registrou o problema como o risco **R1** do plano.

Repare no comportamento: o agente **não mudou a spec por conta própria**. Ele seguiu a spec, apontou o conflito e deixou a decisão comigo. É assim que tem que ser: a spec manda, mas o plano tem a obrigação de avisar quando ela contradiz o mundo real.

:::note[Transparência]
O limite de 50 MB estava escrito no `CLAUDE.md` do meu repositório, que o agente lê em toda sessão (era onde eu registrava o roteiro da cena). Mas o agente não o tirou de lá: ele foi conferir na documentação oficial, como um plano bem-feito deve fazer. Num projeto real, sem nenhuma dica, a pesquisa deve encontrar o mesmo limite, mas eu não testei isso, então não prometo.
:::

### 5. Corrigir onde o erro nasceu: na spec

Eu tinha duas opções: manter os 100 MB e deixar o bug acontecer (para mostrar o fluxo de bugs do Spec Kit), ou corrigir agora. Escolhi corrigir. "O plano pegou o problema antes do código" mostra melhor o valor do SDD do que qualquer bug encenado. Na prática, isso virou o ADR 0009 do laboratório, que substituiu a parte "bug encenado" do ADR anterior.

A correção seguiu a ordem do SDD: **spec primeiro, depois o resto.**

| Arquivo | Mudança |
|---|---|
| `spec.md` | FR-017: 100 MB para **50 MB**; caso extremo atualizado; a resposta na seção `Clarifications` ganhou uma "Emenda pós-plano" (o histórico fica) |
| `research.md` | nota de atualização no R-07; upload com limite de 50 MB |
| `plan.md` | risco R1 marcado como resolvido; resta o limite de 1.000 páginas do Gemini (baixo impacto) |
| `data-model.md`, `contracts/api.md`, `quickstart.md` | 50 MB em todos os lugares |

Quanto custou? Mudar um número em meia dúzia de documentos. Se o erro aparecesse na implementação, seria um bug para investigar, reproduzir e corrigir em código e testes.

### 6. O resto do plano, em resumo

| Decisão | Escolha | Por quê |
|---|---|---|
| Hash de senha | `scrypt` nativo do Node | Princípio II: nada de pacote se o Node já faz |
| JWT | biblioteca `jose` | assinar token à mão é arriscado; `jose` não tem dependências |
| Validação | `zod` nos dois lados | o formulário do shadcn/ui já usa zod |
| PDFs | pasta temporária (multer, limpa no `finally`) e pasta permanente | concilia a constituição (apagar o temporário) com a spec (guardar para download) |
| Tempo-limite da IA | `AbortSignal.timeout(15_000)` | nativo |
| Busca sem acento | coluna normalizada com `normalize("NFD")` | nativo, sem extensão do Postgres |
| Banco de teste | mesmo container, banco `contratos_test` | testes de rota contra banco real |

O Constitution Check passou antes e depois do design, sem violações.

## O que esperar

- Em `specs/001-gestao-contratos-clientes/`: `plan.md`, `research.md`, `data-model.md`, `contracts/api.md` e `quickstart.md`.
- Doze decisões técnicas no `research.md`, cada uma com alternativas descartadas.
- Um Constitution Check sem violações.
- **Em algum lugar do plano, um aviso sobre o limite de PDF do serviço de IA.** Esse é o ponto de conferência deste capítulo.

Para conferir: procure por `50 MB` e `100 MB` em `research.md` e `plan.md`. Se o aviso apareceu, ótimo; corrija a spec e propague.

## Se o seu deu diferente

- **O plano não avisou do limite.** Possível: o modelo e a pesquisa variam. Aí você acabou de pagar o preço de uma etapa pulada, e vale uma aula: peça ao agente para **conferir os limites das APIs externas** contra o `spec.md` e liste os conflitos. O custo de achar agora é o de uma pergunta.
- **O plano avisou, mas sugeriu outra correção** (ex.: trocar inline por File API). O limite de 50 MB vale para qualquer forma de envio, então isso não resolve. Corrija na spec.
- **As versões de pacotes são diferentes das minhas.** Normal. O plano registra a que ele conferiu no npm naquele dia. Anote a sua e use a do seu `research.md`.
- **O Gemini mudou a API outra vez.** É o risco de depender de serviço externo. O plano tem a alternativa registrada; o que importa é você escolher uma e anotar o motivo.

Para retomar do meu ponto: `git checkout fase-3-planejamento`.

## O que isso mostrou

- **A pesquisa do plano não é burocracia.** É onde a spec encontra o mundo real.
- **Quando o plano aponta um conflito, a correção começa na spec.** Código vem depois.
- **Errar num documento custa uma linha. Errar em produção custa um dia.**
- **O agente não deve consertar a spec sozinho.** O que ele fez de certo foi seguir a spec e levantar a mão.
- **Encenar um bug não deu certo, e tudo bem.** Eu planejei esse bug para mostrar o fluxo de correção do Spec Kit. O plano o matou antes. Prefiro o resultado real a uma cena ensaiada.

## Gancho

O plano está pronto, mas é só texto: cinco documentos, nenhuma tarefa que alguém possa executar. Falta quebrar tudo em tarefas pequenas, na ordem certa, com critério de pronto. E, antes de deixar subagentes escreverem código, um último comando vai ler tudo e tentar achar o que ficou inconsistente.
