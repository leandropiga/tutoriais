**Tag de chegada:** `fase-0-setup`.

:::

## O que vamos fazer e por quê

Vamos instalar duas ferramentas e conectar o Claude Code ao GitHub, para ele mesmo criar repositório, fazer commit e push.

:::note[Isto é parte dos meus estudos]
Eu usei **dois** frameworks de SDD juntos porque quis testar a divisão de trabalho entre eles. Não estou dizendo que é o jeito certo, nem que um framework só não resolveria. Existem outras opções (OpenSpec, BMAD, o próprio Kiro).
:::

A divisão que eu quis testar:

| Ferramenta | Cuida de | O que ela entrega |
|---|---|---|
| **Spec Kit** (GitHub) | o **quê**: o que o sistema deve fazer | arquivos que ficam no repositório: constituição, spec, plano, tarefas |
| **Superpowers** (plugin do Claude Code) | o **como**: a disciplina na hora de implementar | TDD, worktrees, subagentes e revisão de código |

Por que os dois? Porque cada um sozinho deixa uma lacuna, pelo menos no meu entendimento:

- Só o Spec Kit gera ótimos documentos, mas **não obriga** o agente a seguir uma disciplina quando ele escreve o código.
- Só o Superpowers impõe a disciplina de implementação, mas o plano que ele gera é **temporário**. Não sobra uma spec viva no repositório.

Juntos: o Spec Kit produz os artefatos duráveis (fases 2 a 4 deste tutorial) e o Superpowers executa o `tasks.md` com disciplina (da fase 5 em diante). Como *tradeoff* custo é concreto: duas ferramentas para instalar e entender, e uma implementação mais lenta e mais cara em tokens, em troca de menos retrabalho. Se o balanço compensa para você, só dá para saber testando.

Alguns termos que vão aparecer, para você não tropeçar:

- **Spec Kit** gera **constituição** (as regras do projeto, que valem para tudo), **spec** (o que construir, por histórias), **plano** (como construir) e **tarefas** (a lista de trabalho). Cada um tem um capítulo.
- **Superpowers** traz **skills** (instruções que o Claude Code carrega sob demanda) para brainstorming, planos, TDD e subagentes.

Os comandos abaixo funcionam em Windows, macOS e Linux; onde muda, eu aviso.

### 1. Crie a pasta e inicie o Git

```bash
mkdir tutorial.sdd.contract
cd tutorial.sdd.contract
git init -b main
```

Usei `tutorial.sdd.contract` para não confundir com o repositório do laboratório (`arkhos.labs.sdd.contract`, o meu). O nome é livre.

### 2. Conecte o GitHub (`gh`)

O Claude Code já sabe rodar comandos no terminal. Se o terminal estiver logado no GitHub, o Claude também está. Não precisa de plugin extra.

```powershell
# Windows (PowerShell)
winget install --id GitHub.cli
```

```bash
# macOS
brew install gh
```

Feche e abra o terminal, e faça o login:

```bash
gh --version
gh auth login
```

Respostas que eu dei:

| Pergunta | Resposta |
|---|---|
| Where do you use GitHub? | `GitHub.com` |
| Preferred protocol for Git operations? | `HTTPS` |
| Authenticate Git with your GitHub credentials? | `Yes` |
| How would you like to authenticate? | `Login with a web browser` |

O "Authenticate Git = Yes" importa: faz o `git push` usar o mesmo login do `gh`. Sem isso, o push pediria uma senha, e o Claude travaria esperando você digitar.

```bash
gh auth status
```

Deve aparecer `Logged in to github.com account SEU-USUARIO` e o escopo `repo` entre os escopos do token. Configure também a identidade do Git:

```bash
git config --global user.name "Seu Nome"
git config --global user.email "seu-email@exemplo.com"
```

### 3. Deixe o Claude registrar as decisões

Aqui você **não** cria o `CLAUDE.md` na mão. Quem cria é o Claude, a partir de um prompt. O `CLAUDE.md` é um arquivo que o Claude Code lê no começo de cada sessão, e é nele que entram as regras do projeto. A mais importante para este tutorial: **toda decisão relevante vira um ADR**. ADR (*Architecture Decision Record*) é um arquivo curto que registra o contexto, a decisão e as consequências de uma escolha. Colocar essa regra no `CLAUDE.md` faz o hábito ser automático, porque você não precisa lembrar de pedir.

Abra o Claude Code dentro da pasta que você acabou de criar:

```bash
claude
```

E mande este prompt:

```text
Este repositório é um projeto de estudo de SDD (Spec-Driven Development). Vamos construir,
passo a passo, uma aplicação de gestão de contratos de clientes.

Crie um CLAUDE.md na raiz com estas regras:
- Idioma do projeto e dos documentos: português (pt-BR).
- Toda decisão relevante (escolha de tecnologia, trade-off, desvio do que foi planejado) vira
  um ADR curto em docs/decisoes/, listado em docs/decisoes/README.md.
- Um commit por etapa concluída, com mensagem em português, e push depois de cada commit.
- Ao fim de cada fase, criar a tag fase-N-<nome> e enviá-la ao remoto.

Crie também a pasta docs/decisoes/ com um README (índice) e um modelo de ADR (_template.md).
```

O Claude responde com o `CLAUDE.md` e a pasta `docs/decisoes/`. O texto exato vai variar de uma execução para outra, e tudo bem. O que importa é o `CLAUDE.md` ter, no mínimo, as ideias abaixo:

```markdown
# CLAUDE.md

## Propósito
Projeto de estudo de SDD (Spec-Driven Development): aplicação de gestão de contratos de clientes.
Idioma: português (pt-BR).

## Decisões
Toda decisão relevante vira um ADR curto em `docs/decisoes/` (`NNNN-titulo.md`),
listado em `docs/decisoes/README.md`.

## Git
- Um commit por etapa concluída, em pt-BR. Push após cada commit de etapa.
- Ao fim de cada fase, criar a tag `fase-N-<nome>` e enviá-la ao remoto.
```

Abra o arquivo que o Claude gerou e confira se essas regras estão lá. Se faltar alguma, peça para ele acrescentar, em linguagem natural. Se o resultado ficou muito diferente, tudo bem copiar o bloco acima para dentro do seu `CLAUDE.md`: o importante é a regra das decisões existir.

### 4. (Opcional) Pré-autorize comandos

Por padrão o Claude Code pede permissão antes de rodar comandos. Para não aprovar cada `git commit`, crie `.claude/settings.json` com uma lista do que é liberado e do que é proibido:

```json
{
  "permissions": {
    "allow": [
      "Bash(git status:*)", "Bash(git add:*)", "Bash(git commit:*)",
      "Bash(git push:*)", "Bash(git tag:*)", "Bash(gh repo view:*)"
    ],
    "deny": [
      "Bash(git push --force:*)", "Bash(gh repo delete:*)"
    ]
  }
}
```

Repare que `gh repo create` **não** está na lista liberada. É de propósito: criar repositório publica coisas na internet, então é bom o Claude perguntar antes.

### 5. Instale o Spec Kit

Ele usa o `uv` (gerenciador de pacotes Python). Instale o `uv` em [docs.astral.sh/uv](https://docs.astral.sh/uv/) se ainda não tiver.

```bash
uv tool install specify-cli
specify --version
```

A saída deve mostrar `specify 1.2.0` (ou mais nova). O `uv tool install` **não atualiza** uma ferramenta que já está instalada, então, se aparecer uma versão mais velha, atualize:

```bash
uv tool upgrade specify-cli
specify --version   # specify 1.2.0
```

Inicialize o Spec Kit no repositório:

```bash
specify init --here --integration claude --force --non-interactive
```

| Opção | Para quê |
|---|---|
| `--here` | usa a pasta atual em vez de criar uma nova |
| `--integration claude` | instala os comandos como *skills* do Claude Code, em `.claude/skills/` |
| `--force` | não pergunta "a pasta não está vazia, continuar?" |
| `--non-interactive` | não abre menus; útil quando é o próprio Claude quem roda o comando |

Apareceu isto no projeto:

```text
.specify/
├── memory/constitution.md     # a constituição (por enquanto, um modelo vazio)
├── templates/                 # modelos de spec, plano, tarefas e checklist
├── scripts/powershell/        # scripts que os comandos usam por baixo dos panos
└── workflows/                 # o fluxo padrão do Spec Kit
.claude/skills/
├── speckit-constitution/  speckit-specify/  speckit-clarify/
├── speckit-plan/  speckit-checklist/  speckit-tasks/  speckit-analyze/
├── speckit-implement/  speckit-converge/  speckit-taskstoissues/
```

O script de apoio foi escolhido sozinho: `ps` (PowerShell) no Windows e `sh` em macOS/Linux.

O Spec Kit também aceita **extensões**, que acrescentam comandos e automações, como um fluxo para tratar bugs ou uma branch por funcionalidade. Nenhuma é necessária para o tutorial. Se quiser conhecê-las, veja o [capítulo 13](/tutoriais/ia-no-desenvolvimento/sdd-na-pratica/13-extras-extensoes-plugins-e-skills/).

### 6. Instale o Superpowers

Rode os três comandos, na ordem, dentro da pasta do projeto:

```bash
claude plugin marketplace add obra/superpowers-marketplace
claude plugin install superpowers@superpowers-marketplace --scope project
claude plugin list
```

1. O primeiro registra o marketplace do autor do plugin.
2. O segundo instala o Superpowers a partir dele.
3. O terceiro lista o que está instalado. Deve aparecer `superpowers@superpowers-marketplace` na versão **7.0.0** (ou mais nova).

Use esse marketplace, e não o oficial da Anthropic: quando conferi, o oficial entregava a 6.4.1, sem as correções da 7.0.0.

O `--scope project` grava o plugin em `.claude/settings.json`, que vai para o Git. Quem clonar o repositório recebe a oferta de instalar o mesmo plugin.

### 7. Reinicie o Claude Code

Skills e plugins só são carregados quando a sessão começa. Saia com `/exit` e abra de novo com `claude` (ou `claude --continue`, para retomar a conversa). Digite `/speckit` e confira se os comandos aparecem.

### 8. Crie o repositório no GitHub

Peça ao Claude em linguagem natural. Por exemplo:

```text
Faça o commit de tudo o que criamos até agora e crie um repositório privado no GitHub chamado
tutorial.sdd.contract, já configurando o origin e fazendo o push.
```

Como o `gh repo create` não está na lista liberada (passo 4), o Claude vai pedir a sua confirmação antes de rodar. Por baixo dos panos, ele executa algo assim:

```bash
git add .
git commit -m "chore: setup do projeto e conexao com GitHub"
gh repo create tutorial.sdd.contract --private --source . --remote origin --push
```

Eu usei `--private` durante o desenvolvimento. Se você só quer acompanhar o tutorial, tanto faz; escolha o que preferir. O `--source .` cria o repositório, configura o `origin` e já faz o push, tudo de uma vez.

### 9. Feche a fase com uma tag

```bash
git tag -a fase-0-setup -m "Fase 0 - Setup concluido"
git push origin fase-0-setup
```

É assim que você volta a este ponto com `git checkout fase-0-setup`.

## O que esperar

- `specify --version` mostra `1.2.0` (ou mais nova).
- `claude plugin list` mostra o Superpowers 7.0.0 ou mais novo.
- Depois de reiniciar, `/speckit` lista pelo menos `speckit-constitution`, `speckit-specify`, `speckit-clarify`, `speckit-plan`, `speckit-tasks`, `speckit-analyze` e `speckit-implement`.
- A pasta tem `CLAUDE.md`, `.specify/`, `.claude/` e `docs/decisoes/`, e o repositório existe no GitHub.
- A tag `fase-0-setup` no remoto.

## Divergências comuns

- **`specify --version` mostra uma versão antiga.** Atualize com `uv tool upgrade specify-cli`.
- **Os comandos `/speckit` não aparecem.** Reinicie o Claude Code. Skills só carregam na abertura da sessão.
- **O Superpowers entrega uma versão mais velha ou mais nova que a minha.** Pode acontecer: o plugin evolui. O nome dos comandos pode mudar um pouco. O que importa para o tutorial são os papéis (brainstorming, planos, TDD, subagentes), que se mantêm. Anote a sua versão.
- **O `specify init` avisa para ignorar `.claude/` no Git.** Alguns agentes guardam credenciais ali. Neste tutorial a gente **versiona** `.claude/settings.json` e `.claude/skills/` de propósito, e deixa o que é pessoal (`.claude/settings.local.json`) no `.gitignore`.
- **O `uv` não está instalado ou o Python é diferente.** O `uv` cuida do Python para você. Instale pelo site oficial.
- **O Claude já criou a tag `fase-0-setup` sozinho.** Normal: o `CLAUDE.md` do passo 3 pede uma tag ao fim de cada fase. Confira com `git tag` e `git ls-remote --tags origin` e pule o passo 9.

**Para comparar com o laboratório:** tag [`fase-0-setup`](https://github.com/leandropiga/arkhos.labs.sdd.contract/tree/fase-0-setup). Lá ela já traz a ideação do capítulo 03 junto (veja a nota sobre a ordem das tags na [página inicial](/tutoriais/ia-no-desenvolvimento/sdd-na-pratica/)).

## O que aprendemos

- Conferir a versão **depois** de instalar (`--version`, `plugin list`) evita seguir o tutorial com uma ferramenta desatualizada.
- Ler as notas de versão antes de aceitar o que o marketplace entrega é uma decisão pequena, mas vale o registro: toda divergência do plano original merece um ADR, porque daqui a um mês você não vai lembrar por que escolheu um caminho e não o outro.
- Colocar a regra dos ADRs no `CLAUDE.md` transforma o hábito em padrão: o Claude passa a registrar as decisões sem você pedir.
